# 局面分析行动解释 Implementation Plan

**Goal:** 落实用户批准的三项改进：走法目的、可见的棋盘预览、结论与原因一致。

**Architecture:** 前端根据真实 executeTurn 结果和既有围堵证据解释走法；最多为默认显示的三条路线计算，不添加搜索或修改规则。普通标题和原因都基于当前静态局面，搜索产生的不同判断单独标为后续走势参考。两页共享路线数据，页面分别管理纯预览状态和滚动。

**Tech Stack:** 微信原生小程序、TypeScript、Node test。

## 执行步骤

- [x] 测试先行：吃子是否实际生效（备用棋不足不得宣称吃子）、强制围堵证据与走法匹配、缺少战术证据时不编造目的、静态判断和搜索预测分离。
- [x] 创建 move-purpose.ts：只使用真实棋规执行、双方合法走法和现有威胁证据。解释直接获胜、已验证围堵、吃子、孤棋活动、封锁进展、减少下一手捕获风险；不能验证时说明目的尚未确认。
- [x] 修改 presentation：当前棋盘标题取静态评分，搜索分档不同且完成搜索时单独显示后续参考；终局和已验证获胜机会仍优先。
- [x] 默认三条路线补充目的说明，更多候选不启动额外计算。
- [x] 独立页只保留一个公共棋盘，点击推荐或备选设置预览说明并滚动到棋盘，提供清除预览；新的分析重置预览。
- [x] 对局页增加预览状态、目的和清除入口，点击后滚动到棋盘；正常棋局状态更新时恢复原有棋盘映射。
- [x] 验证相关测试、类型与结构；审查最新增量；保留所有此前工作区修改，不提交或发布。

## 验收边界

预览不执行落子，不改变棋局或发起落子请求；目的只描述已验证的当前变化，多手保证必须有与该步匹配的现有证明。浅层搜索分数不用于编造对手动作；静态原因不冒充搜索后局面的原因。滑动定位在 setData 完成后发生，预览选中路线与标记一致。

## 验证结果

71 项相关测试通过，类型与结构检查通过，独立代码审查未发现重要问题。已统一终局各页签对实际败方的称呼。未进行微信实际渲染或真机验收。
