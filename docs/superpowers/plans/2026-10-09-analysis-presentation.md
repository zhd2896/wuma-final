# 局面分析展示调整 Implementation Plan

**Goal:** 把用户已确认的建议落实为局面结论、真实原因、可点击推荐和折叠分析依据。

**Architecture:** 保留 AI 和规则计算。共享 analysis-view-model 生成面向玩家的说明，evaluation-panel 在对局页和独立页复用。原始数值只在展开详情后显示，移除固定优势条。

**Tech Stack:** 微信原生小程序、TypeScript、Node test。

## 执行步骤

- [x] 先扩展 analysis-view-model 测试：验证劣势解释、你/AI 视角、同分候选、终局与搜索有限状态，运行确认失败。
- [x] 新建 analysis-presentation.ts：由真实棋子数量、分项、威胁和搜索结果生成结论与最多三条原因。普通分数的展示分档为绝对值 150/400，属于展示约定，不是胜率；终局和强制围堵证据优先于分档。
- [x] 扩展共享映射：保留原始字段，添加一位小数的详情文本和玩家称呼；同分候选标记“当前分析下相当”，不称唯一最佳。
- [x] 更新 evaluation-panel：默认呈现结论、原因、推荐及备选；展开显示两种评分、分项计算依据、候选评分与搜索信息；删除固定优势条。选择走法只触发棋盘标记，不落子。
- [x] 接入 game 和 analysis 页面。分析选线更新棋盘引导，正常落子后继续遵循原有棋盘映射；新分析重置详情。
- [x] 运行相关分析/对局/围堵测试、npm run typecheck、npm run check，并进行代码审查。保留工作区原有未提交改动，不提交或发布。

## 验收边界

没有终局或强制路线证据不得写“已胜/必胜”；无捕获信号不得写“安全”；不同视角不会改变搜索原始评分；静态分项只解释当前静态总分；技术详情不显示胜率。界面使用你/AI 或黑方/红方，候选说明使用已有棋盘位置名称。
