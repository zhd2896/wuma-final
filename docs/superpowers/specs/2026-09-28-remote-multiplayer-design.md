# 远程双人联机设计

日期：2026-09-28

## 目标与范围

两台设备分别持有服务端签发的 A/B 席位凭证，通过邀请码或公开匹配进入同一局；双方只能操作自己的棋子。建房、加入、匹配、取消等待、离开重连、版本同步与终局历史均属于本阶段。旧服务器 `LOCAL` 双人棋局保留为历史兼容，不再由首页“远程双人”入口创建。

本阶段采用用户选定的**设备房间凭证**。凭证是随机生成的高熵 bearer token，本机保存明文，服务器只保存 SHA-256 摘要。它证明某台设备持有 A 或 B 席位，不构成微信账号或跨设备身份；丢失本机凭证后不能凭邀请码认领已有席位。

## 服务端

- 新增 `REMOTE` 棋局模式，以及 `remote_rooms` 表。房间以棋局 ID 为主键，保存唯一邀请码、公开匹配标记、A/B 凭证摘要、A/B 设备标识、等待/对局/取消状态和邀请码到期时间。建房时在一个事务中创建权威初始棋局和等待房间；加入时使用行锁只允许一个 B 席位领取凭证。
- `POST /api/v1/remote/rooms` 建私有房；`POST /api/v1/remote/join` 用邀请码加入；`POST /api/v1/remote/match` 加入一个未过期的公开等待房，若没有则创建公开等待房；`POST /api/v1/remote/rooms/{game_id}/cancel` 允许等待中的 A 取消。A/B 使用 `X-Room-Token` 读取房间、合法走法和提交落子。
- 只有房间为对局中、请求凭证对应当前执棋方、预期版本等于服务器版本时才能落子。`client_request_id` 写入棋步行并由 `(game_id, client_request_id)` 唯一约束保护；相同 ID 与相同走法重试返回原结果，ID 相同而走法不同拒绝。数据库事务中再次校验房间、席位与版本，然后原子写入棋局新状态和棋步。所有棋规仍由现有 TypeScript 引擎执行。
- 房间读取返回权威状态、版本、本人席位、房间状态和邀请码。前端每 3 秒轮询，仅在页面可见时执行；再次显示页面立即拉取。通用 `/api/v1/game/{id}` 的读取、合法走法、落子、复盘与局面分析均不允许操作 `REMOTE`，避免绕过席位校验。

## 小程序

- 首页“远程双人”进入独立的联机页面，提供建房、输入邀请码、公开匹配、等待对手、复制/分享邀请码、取消等待、棋盘与重连状态。本机存储每个房间的席位凭证和最近活动房间 ID；历史索引新增 `online` 模式，进行中与已结束的联机棋局按 ID 返回该页面。已结束棋局先显示终局棋盘，完整复盘接入留待后续阶段。
- 本人轮到走棋且房间已满时才允许点选本人棋子；合法位置和落子均请求后端。对手落子通过可见页面轮询更新同一版本棋盘，页面隐藏和卸载时停止轮询。网络失败展示重试，不在本机推演出一条未被服务器确认的棋步。

## 验收

两份独立客户端本机存储可以完成建房/加入和公开匹配；A/B 各自只能在对应回合走棋；双方看到相同版本；同一请求重试不产生第二手；过期版本、错误凭证、第三人加入、自行加入自己的公开房间均被拒绝；退出重进恢复原席位和棋局。后端内存测试与前端控制器/页面测试必须通过，真实 MySQL 和两设备端到端测试需要隔离数据库与两台可用客户端。
