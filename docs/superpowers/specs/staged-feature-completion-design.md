# 剩余功能分阶段完善设计

用户已经选择把检查清单逐项实施，并要求上一阶段完成后再进入下一阶段。采用依赖顺序实施，而非同时修改全部页面。另一种按页面完成的方式会重复改动训练权限和联机记录；先做纯界面会留下数据无法保存的缺口。因此以真实用户和持久化链路为基础，每阶段交付独立可用的功能。

## 已有实现与范围

当前基线已合并微信登录和真实对局操作。第一阶段只复核已知复盘导航问题和回归；不重新实现悔棋、认输或设置。后续范围是联机账号、训练与题库、棋力、离线棋谱同步、复盘回放与视角、联机学习、多档 AI、个人资料和发布检查。

## 架构约束

1. 后端继续通过唯一 TypeScript 棋规引擎验证棋步与局面；客户端上传的胜负、分数或账号标识不作为可信依据。
2. 普通棋局归属沿用账号鉴权；联机增加双方参与者绑定，保留席位令牌，跨设备恢复由账号与已存参与者关系决定，不能凭客户端设备 ID 认领旧棋局。
3. 训练区分精选公开题源与私有复盘题源；答案只在提交后返回。进度按当前用户、题目统计，作答次数与完成题数分开。
4. 棋力沿用现有六项公式设计和最低样本量，不显示固定能力分数。
5. 本地棋谱保存有效有序棋步；后端导入逐手重演，使用用户范围内幂等键。旧存档缺少历史棋步时明确说明，不能伪造过去棋谱。
6. 回放只读且有权限校验。视角改变须同时影响评分、解释和训练；联机默认本人视角。
7. AI 难度只影响对弈搜索预算，复盘与训练配置保持独立。
8. 个人资料由用户主动填写，登录不假定可以自动获取微信昵称头像。密钥仅在后端，发布检查不能替代真实 HTTPS 地址或微信平台配置。

## 阶段与验收

顺序、状态和证据统一记录到 `docs/staged-feature-progress.md`。每阶段补充具体设计与可执行计划，先运行缺口测试，完成实现后运行相关前后端行为测试、类型检查、页面检查和审查；有数据库结构改动时新增迁移和持久化测试。新变更涉及旧功能时运行回归。所有阶段完成后运行全量测试。

外部验收与代码交付分开：真实微信账号、两台真机和生产部署不得用 Mock 或同模拟器席位切换替代，也不因缺少这些条件停掉独立的代码完善工作。不得宣称尚未执行的测试通过。
