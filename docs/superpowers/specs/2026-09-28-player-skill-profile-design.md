# 《弈智五马》“我的棋力”真实数据设计

**日期：** 2026-09-28  
**阶段：** 我的棋力  
**状态：** 待审核

## 1. 背景与目标

“我的”页面已能读取匿名设备账号的云端对局、复盘和训练统计，但“能力分析”仍固定显示“数据不足”，页面顶部棋力印章也固定为“初”。项目没有一套可解释、可重复计算的棋力规则，因此不能继续展示原演示版本中的虚构能力值。

本阶段用已经真实落库的数据生成个人棋力画像。画像包含六项 0～100 分的启发式指标、综合等级、样本数量和计算版本。每项指标必须独立判断样本是否充足；没有证据时显示“数据不足”，不得补默认分、随机分或演示值。

本阶段不引入 Elo、排行榜或跨设备账号合并。“棋力”只表示当前匿名设备账号在现有对局、复盘与训练数据下的内部画像，不声称是官方段位。

## 2. 数据归属边界

### 2.1 可计入的数据

- 实战结果：当前账号拥有的、已经结束的 AI 对局。
- 复盘数据：上述 AI 对局中，人类一方在当前复盘配置版本下的复盘结果和逐步评价。
- 训练数据：当前账号拥有的训练作答记录。

### 2.2 不计入的数据

- 本地双人对局不计入棋力画像。当前数据模型只能证明设备账号拥有棋局，不能证明账号本人执 A 方还是 B 方。
- 远程双人尚未实现，不纳入本阶段。
- 未结束、放弃但没有结果、没有真实复盘记录的棋局不计入对应指标。
- 旧复盘配置版本不得与当前版本混算。

页面现有的“云端对局”“本机历史”等统计可以继续按原口径展示；棋力画像使用独立的 `evidence` 口径，避免把无法归属到个人执棋方的数据误算为个人能力。

## 3. 版本化计算规则

新增纯计算模块 `backend/app/services/player_skill.py`，由内存存储和 MySQL 存储共同调用。配置版本命名为 `player_skill_v1`，包含复盘版本、样本门槛、分数换算参数和等级区间。任何公式或门槛变化都必须提升版本，防止同一版本名称产生不同结果。

### 3.1 输入证据

计算器接收已经按账号和归属规则聚合的证据：

- `wins`、`losses`
- `training_attempts`、`training_correct`
- `reviewed_games`、`reviewed_moves`
- `good_moves`、`normal_moves`、`mistakes`、`blunders`
- `best_equivalent_moves`
- `score_loss_sum`

所有计数必须为非负整数，分数损失总和必须为非负数。计算器对异常输入做防御性校验，分母为零时返回数据不足。

### 3.2 六项能力指标

| 指标 | 最小样本 | 0～100 分计算方式 | 解释 |
| --- | --- | --- | --- |
| 实战表现 | 已结束 AI 对局不少于 5 局 | `round_half_up(100 × wins / (wins + losses))` | 对 AI 的真实胜率 |
| 最佳着率 | AI 复盘不少于 3 局且复盘着数不少于 15 手 | `round_half_up(100 × best_equivalent_moves / reviewed_moves)` | 与引擎最佳着等价的比例 |
| 决策质量 | AI 复盘不少于 3 局且复盘着数不少于 15 手 | `round_half_up(100 × (1 - min(avg_score_loss, 200) / 200))` | 平均分数损失越低，分数越高；200 是 v1 的封顶损失 |
| 稳定性 | AI 复盘不少于 3 局且复盘着数不少于 15 手 | `round_half_up(100 × (good_moves + normal_moves) / reviewed_moves)` | 保持在正常及以上质量的着法比例 |
| 失误控制 | AI 复盘不少于 3 局且复盘着数不少于 15 手 | `round_half_up(100 × (1 - (mistakes + 2 × blunders) / (2 × reviewed_moves)))` | 严重失误按普通失误的两倍扣分 |
| 训练掌握 | 训练作答不少于 5 题 | `round_half_up(100 × training_correct / training_attempts)` | 真实训练正确率 |

其中 `avg_score_loss = score_loss_sum / reviewed_moves`。`round_half_up(x)` 明确定义为非负数的 `floor(x + 0.5)`，避免 Python 银行家舍入造成半分边界不一致。所有结果限制在 0～100。`reviewed_games` 只统计至少含一条人类着法评价的复盘。`best_equivalent_moves` 在内存数据中使用 `bestMoveEquivalent`；MySQL 中使用 `score_loss = 0` 的逐步记录计算，两种实现必须由一致性测试证明等价。

这些指标有意保留各自的原始含义。最佳着率衡量最优选择，决策质量衡量平均损失，稳定性衡量可接受着法比例，失误控制额外惩罚严重失误。

### 3.3 综合等级

只有六项指标全部达到各自最小样本时才生成综合分。综合分为六项指标的算术平均值，四舍五入到整数：

| 综合分 | 等级 | 印章文字 |
| --- | --- | --- |
| 0～39 | 入门 | 入 |
| 40～59 | 进阶 | 进 |
| 60～74 | 熟练 | 熟 |
| 75～89 | 精通 | 精 |
| 90～100 | 卓越 | 卓 |

任意一项样本不足时，综合分为 `null`，等级为“待评估”，印章显示“待”。页面仍显示已经有充分证据的单项分数，便于用户看到进展。

## 4. API 契约

沿用 `GET /api/v1/me/profile`，在现有个人统计后新增 `skillProfile`，不增加第二个请求：

```json
{
  "id": "...",
  "nickname": "棋手...",
  "games": 8,
  "finishedGames": 6,
  "wins": 4,
  "losses": 2,
  "reviewedGames": 4,
  "training": 9,
  "correct": 7,
  "skillProfile": {
    "version": "player_skill_v1",
    "ready": true,
    "overall": 72,
    "level": "熟练",
    "seal": "熟",
    "metrics": [
      {
        "key": "performance",
        "label": "实战表现",
        "value": 67,
        "sampleCount": 6,
        "minimumSample": 5,
        "sampleUnit": "局",
        "sampleDetails": [
          {"label": "AI 对局", "count": 6, "minimum": 5, "unit": "局"}
        ],
        "description": "AI 对局胜率"
      }
    ],
    "evidence": {
      "aiFinished": 6,
      "reviewedGames": 4,
      "reviewedMoves": 38,
      "trainingAttempts": 9
    },
    "disclaimer": "根据当前账号的实战、复盘和训练记录计算，仅作为弈智五马内的能力参考。"
  }
}
```

`metrics` 固定按六项指标的展示顺序返回。样本不足时，`value` 为 `null`；`sampleCount`、`minimumSample`、`sampleUnit` 和 `sampleDetails` 仍必须返回。实战与训练指标的 `sampleDetails` 含一个门槛；复盘类指标含“复盘局数”和“复盘着数”两个门槛。页面使用 `sampleDetails` 显示完整证据，不能只显示其中一个条件。顶层三个样本字段保留为该指标的主要进度，便于现有页面简单展示。

后端继续保留现有顶层字段，避免破坏已有调用方。小程序的 `PersonalProfileDto` 同步增加严格类型，不能用可选字段或前端默认演示数据掩盖接口遗漏。

## 5. 后端实现

### 5.1 公共计算器

`player_skill.py` 负责：

1. 校验证据；
2. 按 `player_skill_v1` 计算六项指标；
3. 判断每项样本是否达标；
4. 计算综合分、等级和印章；
5. 输出稳定的 API 字典结构。

计算器不读取数据库，也不依赖 FastAPI，便于单元测试并确保两种存储实现共用一套规则。

### 5.2 内存存储

`InMemoryGameStore.personal_profile` 在现有基础统计外：

- 遍历当前账号拥有且已结束的 AI 对局；
- 根据 `ai_player` 确定人类一方；
- 只选取当前复盘配置版本的人类复盘；
- 每局每版本只计一次，聚合逐步类别、最佳着和分数损失；
- 聚合当前账号训练记录；
- 将证据交给公共计算器。

### 5.3 MySQL 存储

`MySQLGameStore._personal_profile` 用数据库聚合查询取得同样证据。查询必须同时约束：

- `games.user_id = 当前账号`；
- `games.mode = AI`；
- 对局已经结束；
- `game_reviews.reviewed_player` 是与 `games.ai_player` 相反的人类方；
- `game_reviews.review_config_version` 是 `player_skill_v1` 指定的复盘版本。

逐步数据通过 `move_reviews` 聚合分类数量、`score_loss` 总和与零损失着数。实现使用固定数量的聚合查询，不把所有历史逐行加载到 Python。无须新增表或数据库迁移。

## 6. 小程序页面

### 6.1 展示

- 顶部固定“初”改为 API 返回的印章；旁边显示综合等级和综合分，未就绪时显示“待评估”。
- “能力分析”区域恢复六项指标，按 API 固定顺序渲染。
- 有分数时显示整数分和等比例进度条。
- 数据不足时显示“数据不足”，并显示进度，例如“2/5 局”；复盘指标同时显示“2/3 局 · 11/15 手”。
- 页面底部展示接口返回的说明文字，让用户知道这是项目内部能力参考。
- 删除遗留的演示开关、演示提示和未使用样式，不保留任何静态能力值。

### 6.2 加载和刷新

页面沿用匿名设备令牌请求个人资料，并在每次 `onShow` 时刷新。增加请求代次保护：重试或快速切换账号触发多个请求时，只有最后一次请求可以更新页面，避免旧账号的慢响应覆盖新账号数据。

错误状态继续提供重试按钮。请求失败时不得把上一次账号的棋力数据继续显示为当前结果。

## 7. 测试与验收

### 7.1 后端测试

- 纯计算器覆盖每项公式、边界值、四舍五入、0 和 100 限制。
- 每项样本少一个时仅该项为数据不足；所有条件满足时才生成综合等级。
- 严重失误比普通失误扣分更高。
- 无记录、零分母和异常负数输入不会生成虚假分数。
- 内存存储只计算当前账号的 AI 人类方复盘，排除本地双人、其他账号、AI 方和旧配置复盘。
- MySQL 持久化测试用相同证据验证结果与内存存储一致，并验证账号隔离。
- 现有账号、历史、复盘和训练测试继续通过。

### 7.2 小程序测试

- API 类型包含完整 `skillProfile` 契约。
- 六项有值时正确展示分数、进度条、等级和印章。
- 部分样本不足时只隐藏对应分数，并展示真实样本进度。
- 全部不足时显示“待评估”，页面源码不存在旧演示评分。
- 两次并发加载乱序返回时，旧响应不能覆盖新响应。
- 请求失败后清除旧棋力并可重试。

### 7.3 手工验收

1. 新匿名账号打开“我的”，六项均显示真实的 0 样本进度，综合等级为“待评估”。
2. 完成未达到门槛的数据后，只更新相关样本进度，不提前给分。
3. 达到某项门槛后，该项出现真实分数；其他未达标项继续显示数据不足。
4. 六项全部达标后出现综合分、等级和动态印章。
5. 新增一局、完成复盘或提交训练后，再次进入页面，指标基于最新记录重新计算。
6. 重启后端并重新打开小程序，MySQL 模式下结果保持一致。
7. 切换匿名账号后看不到前一个账号的棋力与证据。

## 8. 完成标准

满足以下条件才可判定“我的棋力”阶段完成并进入下一阶段：

- 六项指标均由真实账号数据计算，公式和版本可追溯；
- 内存与 MySQL 两种存储返回一致的结构和结果；
- 样本不足按单项显示，页面没有虚构评分；
- 本地双人数据没有被错误归属为个人棋力；
- 综合等级只在全部门槛满足时出现；
- 自动化测试通过，开发者工具完成新账号空状态和真实账号刷新验收；
- README 或项目阶段文档更新了真实计算口径和限制。
