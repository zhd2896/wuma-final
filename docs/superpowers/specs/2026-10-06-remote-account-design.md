# 阶段二：联机账号归属设计

## 目标与方案

建房、加入、匹配绑定已认证用户；两名参与者均能在个人历史看到棋局、自己的席位与结果，同一微信账号换设备后能恢复。保留房间令牌，不把设备 ID 当账号。采用房间的 `host_user_id` / `guest_user_id` 两个可空用户外键，兼容旧设备席位。

单一 `games.user_id` 不能表达两名参与者；凭客户端设备 ID 认领旧房间会产生越权，因此不采用这两种替代方式。

## 权限和兼容

- 生产鉴权开启时，创建、加入与匹配必须有有效账号；服务端把账号传到同一房间事务，不接受客户端指定用户 ID。
- 同账号不能同时占 A/B，不能通过换设备 ID 加入自己房间；公开匹配跳过本人房间。
- 对已绑定席位，房间读写同时验证当前账号与房间令牌所属席位。令牌不能帮助不同账号操作已绑定的棋局。
- 旧未绑定席位可由原令牌持有者显式认领到当前账号；已绑定他人账号的席位不可重新认领，不能仅凭邀请码、棋局 ID 或设备 ID 认领。
- 当前账号已绑定房间但本机没有令牌时，可请求恢复本人席位。服务端轮换该席位令牌，返回权威房间状态；非参与者拒绝。同设备有效令牌恢复保持现有路径。
- 账号迁移须一并迁移参与者外键，避免匿名升级微信后记录丢失；处理目标账号已经占另一席位的冲突，不能形成双方同账号的棋局。
- 显式 `require_auth=False` 的引擎/旧流程测试保留无账号兼容；默认生产设置保持需要账号。

## 数据、接口与页面

新增迁移衔接唯一 head `0014_merge_auth_operations`，仅新增可空参与者字段和索引，不自动推测旧房间归属。储存协议、内存实现与 MySQL 事务实现行为一致。

个人分页历史按“普通所有者或联机参与者”查询，去重、稳定排序，返回 `mode=REMOTE` 和本人 `seat`。联机已结束记录打开既有席位复盘，进行中记录进入联机恢复。

个人统计云端对局数包含已归属联机局；保留现有 `wins` / `losses` 的 AI 统计含义，新增联机对局及胜负字段并明确页面标签，后续棋力公式继续只使用 AI 样本。

前端跨设备打开云端联机记录时，无本机房间凭证可凭当前登录账号恢复；从旧设备历史恢复时，可在证明旧令牌后认领。当前用户无资格时保留清晰错误，不能退回无鉴权路径。

## 验收

账号 A 建房、B 加入后双方列表有记录、第三人无记录且不能恢复/操作；A 换设备可恢复 A，不能恢复 B；同账号换设备加入自己房间被拒绝，匹配不匹配本人；旧令牌认领、已绑定席位不可被抢占、账号迁移与历史分页验证一致；AI 基础统计不回归。

测试先覆盖上述缺口，再实现 API、存储事务及前端恢复。验证真实 MySQL 迁移和持久化，前端控制器/历史路由，以及相关原有测试。真实两设备验收单独记录。
