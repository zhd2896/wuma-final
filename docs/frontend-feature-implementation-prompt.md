# 弈智五马：前端未完成功能实施总提示词

> 将本文交给负责实现的编码助手。它是一份总任务说明，涵盖页面、服务、后端接口、数据迁移与验收；每个里程碑都应形成可以独立运行的结果。本文基于 2026-09-27 的仓库代码。

## 总任务

请在本仓库把现有微信原生小程序从“部分真实功能 + 演示页面”完善为可实际使用的五马棋产品。前端位于 `miniprogram/`，后端为 `backend/app/` 中的 FastAPI + MySQL；棋规以 `miniprogram/domain/` 的 TypeScript 引擎为唯一权威，后端通过 `backend/engine_worker.mjs` 调用同一引擎。先阅读 `README.md`、`backend/README.md`、现有测试以及本文列出的源文件，再按下方顺序实施。

完成一项功能时，请同时更新前端交互、API 契约、后端路由与服务、数据库迁移、必要的测试及 README。保留已经可用的本地走棋、AI 自动应手、AI 局面分析、三级教练提示、真实复盘解释和复盘训练。对所有异步页面提供加载、空结果、错误、重试状态；对重复提交和过期棋局版本作明确处理。新接口沿用 `{code, message, data}` 响应格式，前端沿用 `miniprogram/services/api-client.ts`，不要在正式页面继续展示 `miniprogram/mock/` 的固定业务数据。

每完成一个里程碑，报告改动文件、接口/迁移、已运行的验证命令及结果，再进入下一里程碑。以下“建议新增文件”可以依项目习惯调整，但职责、接口与验收行为必须保留。

## 现状与依赖顺序

1. **先解决身份与数据归属**：历史、个人统计、跨设备续局和真正的双人联机依赖稳定玩家身份。目前 `users` 表存在，但新棋局和训练记录的 `user_id` 写为 `None`。
2. **再打通历史与页面入口**：真实棋局列表是首页复盘、独立分析和教练页选择棋局的基础。当前历史页读取 Mock，且传给复盘页的参数名错误。
3. **再实现对局操作与联机**：保留原有离线本地模式和 AI 模式；将目前由同一客户端操作两方的“远程双人”升级为两名玩家各操一方。
4. **最后完善内容与发布**：独立分析/教练、能力统计、经典残局、复盘棋盘回放、AI 难度和正式环境 API 配置。

## 里程碑一：身份、历史与入口

### 1. 用户登录、鉴权和数据归属

**现状**：`backend/app/db/models.py` 定义了 `UserModel`，但 `backend/app/db/repositories/game.py` 创建棋局时把 `user_id` 设为空；`backend/app/db/repositories/training.py` 的答题记录也没有用户。前端没有登录会话。

**修改方式**：

- 在小程序启动流程加入 `wx.login`；后端新增微信登录接口，以服务端保存的 AppID/密钥换取稳定的微信用户标识，创建或读取 `users` 记录并签发会话令牌。密钥只放后端环境变量。前端新增 `miniprogram/services/auth-api.ts` 和会话管理模块，在 `api-client.ts` 中附带令牌；过期时重新登录并重试一次安全的读取请求。
- 新增 FastAPI 鉴权依赖，创建棋局和答题时写入当前 `user_id`。读取、落子、分析、教练提示、复盘、生成训练题等按参与者或资源所有者做后端权限校验，不能只凭 `game_id` 访问或修改他人数据。更新 `GameStore` 协议、MySQL 实现、内存测试实现及数据库迁移。
- 保留旧匿名记录供数据库兼容，但不因知道旧 `game_id` 就自动认领；个人列表只返回已归属的记录。为开发者工具和自动化测试提供明确的测试登录方式，正式环境不得接受测试身份。

**验收**：互不相关的两个用户不能读取或修改对方的棋局、复盘和训练记录；远程棋局的两名参与者可以按各自权限访问同一棋局；同一用户重登后能取回自己的棋局；旧匿名数据不混入个人统计；现有后端测试更新后通过。

### 2. 真实历史对局与继续对弈

**现状**：`miniprogram/pages/history/history.ts` 使用 `historyService.getHistory()` 返回固定记录；`openReview` 传 `?id=`，而 `miniprogram/pages/review/review.ts` 读取 `gameId`。目前只有单个活动 AI/远程棋局 ID 存在小程序本地存储中。

**修改方式**：

- 后端新增分页的 `GET /api/v1/me/games`，按当前用户过滤，返回棋局 ID、模式、双方身份、状态、胜方、开始/结束时间、步数、是否已有复盘和下一页游标；定义稳定排序，避免翻页时重复或漏项。前端新增历史 API 与 DTO，替换 `historyService` Mock。
- 历史页展示真实加载/空/错误/重试状态及分页。进行中的棋局打开对应模式并按指定 `gameId` 恢复；已结束的棋局打开 `/pages/review/review?gameId=<真实ID>`。修改 `game.ts`、`ai-game.ts`、`remote-game.ts`，支持显式 `gameId`，并在恢复时校验模式与用户权限。
- 删除“预览空状态”开关和“Mock 记录”文案。日期、结果和回合数以服务器数据为准；无复盘的已结束棋局由复盘页现有逻辑生成复盘。

**验收**：新用户看到真实空状态；下完并结束一局后可从历史页找到它、打开复盘；未结束棋局可从历史页继续；`id`/`gameId` 不再错配；分页无重复。

### 3. 首页和教练页的复盘入口

**现状**：`miniprogram/mock/game.ts` 的首页“棋局复盘”卡片以及 `miniprogram/pages/coach/coach.ts` 的“从复盘中继续学习”都直接打开无 `gameId` 的复盘页，最终只显示缺少棋局的错误。

**修改方式**：将两个入口导向带“已结束”筛选的真实历史页，或者打开一个共用的棋局选择页；选中棋局后再传 `gameId` 给复盘页。没有已结束棋局时显示可操作的空状态和“开始对弈”入口。复盘页继续拒绝缺少 ID 的直接访问，但错误文案要指向选择棋局的路径。

**验收**：首页、教练页和历史页三个入口都能在有已结束棋局时打开真实复盘；无棋局时不会出现无法继续操作的死路。

## 里程碑二：对局完整性

### 4. 本地双人存档、历史和复盘

**现状**：`miniprogram/pages/game/local-game.ts` 的棋规与走棋真实可用，但 `game.ts` 每次进入都创建新局，棋步未保存，也无法进入服务器复盘。

**修改方式**：

- 本地模式每步保存版本化的 `GameState`、棋步列表、时间和终局状态至小程序本地存储；进入时校验并恢复，提供“继续本局”和“重新开始”。存储损坏时给出恢复失败提示并允许新开局。
- 用户登录且联网后，提供“同步本地棋局”流程。新增后端导入接口：只接收初始先手及有序棋步，由 TypeScript 引擎在服务器逐步重演并验证最终状态，再保存为归属该用户的棋局；不要信任客户端上传的胜负或评分。导入使用幂等客户端棋局 ID，防止断网重试生成重复记录。
- 同步成功的本地终局进入现有复盘/训练链路；尚未同步时说明需要联网同步。同步失败不清除本地存档。

**验收**：关闭并重开小程序后本地棋局和棋步仍在；同一局重复同步只生成一条历史记录；篡改棋步被拒绝；同步后的终局可复盘。

### 5. 悔棋、认输与设置

**现状**：`miniprogram/pages/game/game.ts` 的 `undo()` 只弹提示；`resign()` 没有页面按钮入口，`confirmResign()` 仅显示演示 Toast；`game.wxml` 的确认文案仍称 UI 演示；设置区大多只显示当前模式。

**修改方式**：

- 明确各模式规则并实现：本地悔棋回退一步且同步本地存档；AI 悔棋回退最近一组“玩家走棋 + AI 应手”；远程双人悔棋采用对手同意请求，在对手接受前双方棋盘不回退。服务器必须验证棋步、版本和双方权限，原子更新棋局与历史，重复请求可安全处理。
- 对 AI/远程棋局新增后端认输接口，写入真实终局事件、胜方和 `RESIGN` 终局原因，扩展后端 DTO、数据库及前端显示；认输后禁止继续落子并允许复盘。远程认输由当前参与者本人发起。本地模式提供“结束并保留为弃局”操作，弃局与已完成胜负局分开展示。
- 在页面上添加可见的“认输/结束”入口，替换演示确认文案。设置页只展示和保存真实生效的选项，例如先手、提示显示和音效；没有实现的控件不显示。变更设置不得悄悄覆盖进行中的棋局。

**验收**：各模式悔棋后的棋盘、步数和重开后的状态一致；远程悔棋需双方同意；认输后服务器和历史页均显示真实结果；设置重进页面后仍按用户选择生效。

### 6. 真正的远程双人对战

**现状**：`remote-game.ts` 调用现有 `createGame()` 创建 `LOCAL` 服务器棋局，同一客户端可以操作 A/B 双方；没有房间、匹配、玩家席位和实时同步。

**修改方式**：

- 后端增加 `REMOTE` 模式、棋局参与者/席位和邀请房间数据。提供建房、凭邀请码加入、随机匹配、取消匹配、查看房间/棋局状态接口；邀请码有有效期，满员后不能再加入。用户只能占一个席位，不能替对方落子。
- 落子请求增加预期棋局版本和客户端请求 ID，服务端在同一事务中校验身份、回合、版本并保存棋步；重试同一请求不得重复落子。为小程序提供按版本拉取新状态的接口，首版可用页面可见期间的定时轮询；离开页面暂停，返回时立即同步。不要把 UI 轮询间隔当成回合合法性依据。
- 前端增加建房、分享邀请码、输入邀请码、匹配、等待对手和掉线重连状态。棋盘只允许控制自己的棋子；等待对手时显示其状态。旧的同设备双人玩法保留为“本地双人”，不再使用“远程双人”入口进入旧流程。

**验收**：用两个不同用户的客户端完成建房加入和随机匹配；一方落子后另一方看到同一版本棋盘；越权、重复、过期版本、第三人加入均被拒绝；退出重进后能恢复原席位和棋局。

## 里程碑三：分析、教练与个人成长

### 7. 独立局面分析页接入真实局面

**现状**：`miniprogram/pages/analysis/analysis.ts` 只读取 `analysisDemo` 和固定棋盘；`game.ts` 的本地、远程模式“分析”按钮会打开此演示页。AI 对弈页内已有真实 `/api/v1/ai/analyze` 调用。

**修改方式**：

- 独立分析页接受明确的 `gameId` 或当前本地存档 ID。服务器棋局先读取权威状态和版本，再调用现有分析接口；本地离线棋局复用 `miniprogram/ai/position-analysis.ts` 的引擎计算。把现有三个页签映射到真实评分分项、威胁、候选走法和当前棋盘，不再展示演示推荐线。
- `game.ts` 在跳转时传入对应棋局上下文。分析计算期间防止连续请求；若棋局版本已变化，提示用户刷新并重新计算，不把过期结果显示为当前局面。没有可分析棋局时显示棋局选择/开始入口。
- 将 AI 对弈页的分析结果展示与独立页共用映射逻辑，避免两处对同一字段做不同解释。

**验收**：AI、本地和远程棋局从各自对局页打开分析时展示该局的真实棋盘与结果；落子后再分析可看到新版本；断网时本地分析仍可用。

### 8. 独立 AI 教练页接入真实三级提示

**现状**：`miniprogram/pages/coach/coach.ts` 使用 `coachService` 固定提示。真实教练接口只允许正在进行中的 AI 棋局、玩家回合，AI 对弈页内已调用它。

**修改方式**：教练页接收当前 AI 棋局 `gameId`，没有上下文时从用户进行中的 AI 棋局中选择；没有合适棋局时给出“开始 AI 对弈”入口。读取棋局版本后逐级请求现有 `/api/v1/game/{game_id}/coach/hint`，按一级关注点、二级候选棋子、三级推荐走法展示，棋盘变化后清空旧提示。后端现有“仅 AI 模式且玩家回合”规则保持一致，其他模式显示明确的不可用说明。复盘学习入口按第 3 项打开真实棋局选择。

**验收**：独立教练页与 AI 对弈页对同一棋局版本展示一致的分级提示；旧版本提示不会留在新棋盘上；非 AI 或 AI 行棋时不会展示虚构提示。

### 9. 我的棋力和个人统计

**现状**：`miniprogram/pages/profile/profile.ts` 使用 `profileDemo`，对局数和训练完成数固定；能力图仅通过“UI 演示开关”显示假数据。

**修改方式**：新增 `GET /api/v1/me/profile` 和统计服务，从当前用户已结束棋局、已生成复盘和训练记录计算总对局、胜负、训练完成、正确率及六项能力指标。为每项指标定义可复算的输入与公式，并设置最低样本量；样本不足时显示“数据不足”，不能用演示分数补齐。昵称来自用户资料；如设置棋力等级，定义版本化、可解释的等级计算规则并持久化或可重算。页面删除演示开关，真实数据拉取失败时保留重试入口。

**验收**：新用户所有统计为空/零且不出现假能力值；完成对局、复盘和训练后相应统计变化；不同用户的统计互不影响；同一数据重复请求结果一致。

## 里程碑四：训练、复盘与 AI 体验

### 10. 经典残局、训练分类与个人进度

**现状**：`miniprogram/pages/training/` 的棋盘答题和引擎评分可用，但题目只从复盘失误生成；首页却称“残局挑战”。当前 `difficultyTag` 恒为 `UNCALIBRATED`，列表不显示个人完成状态。

**修改方式**：

- 保留“复盘训练”题源，再新增版本化的人工精选残局题源，标明 `REVIEW`/`CURATED` 来源。精选局面必须通过同一棋规引擎验证有合法解，答案由服务端引擎评分；题目读取接口不得提前返回最佳走法。为精选题和复盘题建立可解释的难度标记，不能把未经校准的题目写成已分级。
- 扩展训练列表接口以支持题源、失误类别、难度和本人完成状态筛选；更新 `training-api.ts`、`training-controller.ts`、训练页标签与分页，筛选变化时清空旧列表并从第一页读取。
- 答题记录绑定用户，提供本人最近结果、完成数和正确率；“下一题”优先跳过当前已完成题。首页“残局挑战”默认进入精选残局，复盘页生成题后进入该局的复盘训练列表。

**验收**：无历史棋局的新用户也能做精选残局；复盘题仍能生成、作答和评分；不同筛选结果与总数一致；同一用户重登能看到自己的答题进度，其他用户看不到。

### 11. 复盘棋盘回放与复盘视角

**现状**：`miniprogram/pages/review/review.wxml` 有真实逐手评分和解释，但无棋盘回放；后端 `GameStore.read_replay()` 和 `GameService.replay_game()` 已有重建棋步的基础。后端允许非 AI 棋局选择 A/B 视角；AI 棋局仅允许人类玩家视角。

**修改方式**：新增受权限保护的有序棋步回放接口，返回初始局面和每手的前后状态、落点、吃子结果及版本。复盘页增加棋盘、上一步/下一步/跳转到第 N 手，选中的逐手解说与棋盘同步；终局和空棋步有明确状态。非 AI 棋局显示 A/B 视角选择，并把 `reviewed_player` 传给已有复盘/解释接口；AI 棋局固定为人类玩家。修改 `miniprogram/services/training-api.ts` 的 `generate()` 和 `review.ts`，把当前复盘视角传给已支持该参数的生成训练题接口，不能切换视角后生成另一方的题。

**验收**：逐手前进/后退时棋子、备用棋和吃子结果与服务器记录一致；A/B 视角对应不同的逐手评价；AI 棋局不能请求 AI 视角复盘；回放不会改变真实棋局。

### 12. AI 难度选择

**现状**：`backend/app/schemas/game.py` 仅允许 `STANDARD`，`game_service.py` 创建 AI 棋局时固定标准级；前端设置仅能改变谁先手。

**修改方式**：定义至少三个版本化难度档位（例如入门、标准、进阶），在后端将档位映射到引擎搜索深度与时间预算，校验资源上限；扩展创建棋局 DTO、持久化字段、AI 计算路径和前端设置。难度在开局时确定，中途更改需明确要求新开局；历史页显示当局实际档位。复盘与训练仍使用自身固定的分析配置，不随对战难度降低准确性。

**验收**：三个档位创建、恢复、显示一致；AI 计算使用对应预算；非法档位被拒绝；现有标准档位棋局及测试继续可用。

## 里程碑五：发布配置和整体收口

### 13. 体验版、正式版 API 与页面文案

**现状**：`miniprogram/config/api.ts` 的 `test`、`production` 地址为空，体验版和正式版会在创建 API 客户端时失败；首页、部分页签和对话框仍写有“UI 演示”“Mock”等文案。

**修改方式**：将实际部署的 HTTPS API 地址分别配置到体验版、正式版构建配置中，并在微信小程序后台配置合法 request 域名；密钥继续只存后端环境。增加构建/发布前配置检查，地址缺失时明确失败。校验 `/ready` 同时覆盖引擎与数据库可用性。逐页删除已完成模块的演示提示，尚未启用的功能显示真实原因。更新 `README.md`、`docs/deployment.md` 的部署与环境说明。

**验收**：开发者工具、体验版、正式版分别连接预期环境；两台真机可登录并完成远程对局；无后端时有可读错误和重试；页面不把真实数据标为演示数据。
