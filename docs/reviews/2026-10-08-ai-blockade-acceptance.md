日期：2026-10-08。分支：`codex/growth-feedback`。本阶段修改尚未提交、合并或部署；保留原有云端 API 配置和上一阶段未提交改动。

## 已实现

1. 复现最新对局第 35 手后的真实局面：A 孤棋 P28；B 为 P01/P05/P06/P14/P17/P23/P25/P26/P27，轮到 B，备用棋 A=4、B=0。入门、标准、进阶均选择能强制完成围堵的合法路线，执行全部对手应手后可真实终局。P05→P03、P28→P29、P03→P28 是其中一条；等效路线也接受。
2. 共享 Minimax/Alpha-Beta 战术延伸最多额外检查两手；限定庙内孤棋且围堵方至少三子的紧凑残局。每个对手合法应手均经真实移动、吃子及换手验证。不会把配合走法或进入庙宇本身判为获胜。
3. 新增围堵进度静态评分，降低残局冗余机动性奖励；评分是启发式，实际胜负仍由规则引擎决定。搜索深度只记录完整基础层，强制围堵威胁另外说明验证的最多棋步。
4. 实际 AI 落子可保留超时前已证明获胜的候选；部分启发式评分不公开。分析和复盘使用最后完整层，避免把新证明与旧层候选混合计算评分损失。
5. 分析页展示强制围堵证据、关键棋子与围堵评分；教练三级提示提供保留封口、调棋收网及真实推荐走法，保留各级点位泄露限制。“保证获胜”等表达必须有搜索证据，不将后续围堵说成本步直接终局。
6. 玩法讲解增加真实三步示例；终局提示明确“换手后全方无合法走法判负”；复盘说明有效围堵、错过的强制围堵及真实庙困结果。
7. 新复盘评分配置 v2、新教练缓存 coach_hint_v2。旧记录不覆盖。已发布精选题明确沿用 v1 分析、复盘及答题评分，避免相同题 ID 的不可变内容冲突。

## 发布后的验收步骤

1. 将本阶段源码与上一阶段全方堵塞规则一同发布到实际后端，并重启 Node worker；本阶段无需数据库新增迁移。编译对应小程序源码。
2. 微信开发者工具中分别以入门、标准、进阶执行同一围堵残局，检查 AI 保留封口棋、调入其他棋子；按真实合法应手继续，最终展示庙困。可通过专用测试库布置上述局面，勿修改正式历史快照。
3. 人类轮次打开分析和三级教练，核对当前棋盘、评分、关键棋子与推荐走法。一级不泄露点位，二级不展示完整路线；三级区分后续强制围堵与本步终局。
4. 终局后查看个人历史、棋谱复盘和讲解；退出重进，核对胜方、终局原因、三手棋谱一致。旧训练题列表与答题应正常，练习记录保留。
5. 实机验证界面文本、编号图与滑动展示；联机若出现全方被堵，双方终局、历史及复盘应一致。AI 专项围堵不意味着联机对手会自动配合。
